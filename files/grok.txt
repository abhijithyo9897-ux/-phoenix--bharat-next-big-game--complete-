Outer dimensions: 95 × 95 × 95 mm (cube) or 90 mm diameter × 110 mm height (cylinder variant).
Weight target: 380–420 g (premium metal-reinforced edition 520–580 g).
Wall thickness: 4.5 mm outer shell, 2.2 mm internal rings.

Ring Architecture (7-layer standard)

Outer decorative shell (fixed).
2–6. Five independently rotating or sliding rings.
Central core lock + code chamber.

Each movable ring carries 12–16 discrete positions with precision detents (0.15 mm engagement depth). Detents give a clear “click” and prevent accidental drift.
Internal Mechanism

Rings ride on a central stainless-steel axle with low-friction PTFE bushings.
Axial load is taken by two thrust washers so rings never bind under compression.
Final lock is a multi-pin solenoid-style mechanical gate (no electronics required for the pure solve). When all rings reach the correct relative angles, the pins retract and the core lid springs open 8 mm under a constant-force spring.

Optional Kinetic Reveal (premium SKU)

Four micro-electromagnets embedded in the base ring.
When the correct combination is reached, a passive magnetic switch closes a circuit powered by a tiny supercapacitor (pre-charged via the Omni-Board or docking station).
Electromagnets fire in a 1.2-second sequence that causes three internal panels to slide and the central core to rotate 90°, exposing the geometric code plate with a theatrical “reveal.”

Materials

Outer shell: glass-filled nylon (PA6-GF30) or aluminium 6061-T6 for metal editions.
Rings: POM (acetal) for low friction and dimensional stability.
Code plate: polycarbonate with laser-etched QR + embossed geometric pattern + embedded NFC NTAG 424 DNA (secure, unique ID).
Ferro-magnetic lattice: thin Mu-metal foil laminated under the outer faces so the box is readable by the Omni-Board’s electromagnetic grid.

Manufacturing Process

Injection mould or CNC the rings and shell.
Laser-etch or tampo-print symbols (role-specific icon sets).
Assemble axle stack with controlled torque.
Program NFC with unique seed + cryptographic signature.
Final functional test: automated robot solves the box 5 times and verifies code plate.
Each unit is registered to the global Saptabhagini ledger before shipping.

Tolerances

Ring concentricity ≤ 0.08 mm.
Detent force 1.8–2.4 N.
Core opening force 4–6 N (comfortable one-finger operation).

1. Core Problem Definition
A polyomino is a connected set of unit squares joined edge-to-edge.
Tiling (or exact cover by polyominoes) asks: given a region $  R  $ (the board) and a multiset of polyominoes $  T  $, does there exist a placement of (rotated/reflected) copies of the pieces in $  T  $ that covers every cell of $  R  $ exactly once, with no overlaps and no pieces extending outside $  R  $?
In Phoenix this is generalized:

The board grows dynamically via successive placements.
Additional hard constraints: Sudoku-style non-adjacency of identical shapes, Magic-Square sum conditions on selected 3×3 windows, reciprocal-grid interlocking (Da Vinci-style), Z-axis stacking, and Go-style enclosure detection.
Soft constraints: load-bearing physics, line-of-sight, and future flood-fill reachability.
All operations must produce immutable boundary DTOs for event-sourcing and rollback.

2. Computational Complexity

General polyomino tiling is NP-complete.
Even restricted cases remain hard:
Tiling with a fixed set of polyominoes (including certain trominoes or bars) is NP-complete.
Tiling simply-connected regions with two rectangles is polynomial in some cases, but NP-complete for larger fixed sets.

Special polynomial cases exist:
Domino tiling of a simply-connected region → perfect matching in a bipartite graph (polynomial).
Fixed-size square tiling ($  k \times k  $) of a polygon given by corners can be decided in $  O(n \log n)  $.

Counting solutions is typically #P-complete.
Plane-tiling (infinite) versions are often undecidable.

For the game engine we therefore never attempt exhaustive search on large boards; we use bounded search, incremental validation, and heuristics.
3. Primary Algorithmic Families
A. Exact Cover + Dancing Links (DLX / Algorithm X) — The Gold Standard
Donald Knuth’s Algorithm X (2000) reduces tiling to the classic Exact Cover problem:

Columns = cells of the board (+ one column per distinct piece if each piece may be used only once).
Rows = every legal placement of every piece (all rotations/reflections, all positions).

Dancing Links (DLX) is the highly efficient implementation using circular doubly-linked lists. Covering/uncovering a column is $  O(1)  $ pointer surgery; the links “dance.”
Strengths for Phoenix

Extremely fast on classic puzzles (pentominoes on 6×10, Tetris Cube, etc.).
Naturally supports “each piece used exactly once” or “unlimited copies.”
Easy to add secondary constraints (optional columns).
Produces all solutions or can be stopped at the first.

Practical performance
Modern DLX implementations solve the classic 12-pentomino 6×10 board in milliseconds and scale well to boards of a few hundred cells when the number of piece types is modest.
Game adaptation

Pre-generate all possible placements of the 7 free tetrominoes (or the larger set used in Phoenix) on the current bounding box.
Maintain an incremental DLX matrix that grows only when new polyominoes are added to the board.
For real-time play we run a depth-limited or time-bounded DLX to answer “is this partial placement still completable?” or “does this move create an immediate enclosure?”

B. Classic Backtracking / Recursive Placement
Simple depth-first search:

Choose an uncovered cell (usually the most constrained).
Try every legal piece placement that covers it.
Recurse; backtrack on failure.

Heuristics that dramatically improve performance:

Minimum Remaining Values (MRV) — always cover the cell with fewest options.
Piece ordering by size or by number of possible placements.
Forward checking / constraint propagation.

This is the method used in many educational solvers and is easy to instrument for immutable state snapshots.
C. Reduction to SAT / SMT
Encode each possible placement as a Boolean variable.
Clauses enforce:

Exactly one placement covers each cell.
At most one placement of each unique piece (if required).
Extra geometric or numeric constraints (Magic Square sums, adjacency bans).

Modern SAT solvers (CaDiCaL, Kissat, CryptoMiniSat, Z3) are competitive with DLX on many instances and excel when additional non-geometric constraints are present. Phoenix already uses constraint solvers for Sudoku/Magic Square layers, so a unified SAT backend is attractive.
D. Integer Linear Programming (ILP)
Binary variables for each placement.
Linear constraints for exact cover + any numeric conditions (sums, load values).
Solved by CPLEX, Gurobi, or open-source solvers.
Recent work shows checkerboard / multi-colouring techniques can split large instances into independent subproblems, enabling parallelism.
Useful for offline balance testing and for generating “perfect ring” challenges, but usually too slow for real-time player moves.
E. Special-Case Polynomial Algorithms

Domino tiling → bipartite matching (Hopcroft–Karp or faster planar methods).
Fixed $  k \times k  $ square tiling of a polygon given by vertices → $  O(n \log n)  $.
These can be used as fast filters or for particular Vitruvian sub-systems (e.g., pure domino scaffolding phases).

2. Heuristic Improvements That Make Bounding Effective
These heuristics shrink the search tree so that a useful answer appears before the budget is exhausted.
A. Minimum Remaining Values (MRV / “S” heuristic)
Always choose the column with the fewest remaining 1s.
Knuth showed this dramatically reduces the number of nodes. It is the single most important optimization and should be enabled by default.
B. Fail-first / Most-constrained ordering
When several columns have the same size, prefer the one whose covering rows also cover other tight columns.
C. Piece / placement ordering
Pre-sort rows so that larger polyominoes or pieces with fewer orientations are tried first. This often forces early contradictions.
D. Forward checking / constraint propagation
After covering a row, immediately check whether any remaining column has dropped to zero. (DLX already does this implicitly via the size counters.)
E. Symmetry breaking

Fix one particular placement of a highly symmetric piece (e.g. the X-pentomino).
Use Burnside / lexicographic ordering on partial solutions.
For polyominoes, generate only one orientation class when the board itself has symmetry.

F. Secondary columns
Knuth’s generalization: primary columns must be covered exactly once; secondary columns may be left uncovered (but never covered more than once). Useful for optional Magic-Square windows or soft load-bearing constraints.
3. Incremental / Dynamic DLX
Full matrix rebuild on every placement is too expensive. Two practical approaches:

Delta patching
Keep the current DLX structure. When a polyomino is placed, permanently cover the corresponding cells/columns and remove the now-illegal rows. On undo (or for a speculative check) reverse the covers. Because dancing links are reversible in O(1) per node, this is cheap.
Sparse / region-of-interest matrix
Only materialize columns for the currently empty cells inside a bounding box around the latest placement plus a small halo. Distant already-solved regions are ignored.

For Phoenix the recommended pattern is:

Maintain a long-lived “master” DLX for the whole board.
For a speculative placement, clone only the affected sub-matrix or apply a reversible delta, run bounded search, then restore.

4. Caching & Memoization

Transposition / Zobrist-style hash of the set of still-uncovered primary columns → cache “this residual problem is unsolvable / solvable”.
ZDD (Zero-suppressed Decision Diagram) acceleration (research result): while searching, build a ZDD of solutions to subproblems; subsequent identical subproblems are answered in constant time from the ZDD cache. Can give orders-of-magnitude speed-ups on highly structured instances.

For real-time use a simple LRU cache of residual column-set hashes is usually sufficient.

textCopyCopied// Core data structures (classic Knuth style + size counters)
struct Node {
    Node *L, *R, *U, *D;   // dancing links
    Column *C;             // column header
    int rowId;             // original placement index (for solution recovery)
};

struct Column {
    Node head;             // circular list of nodes in this column
    Column *L, *R;         // horizontal list of active columns
    int size;              // number of remaining 1s (for MRV)
    bool primary;          // true = must be covered
    int id;                // cell or piece identity
};

// Global / per-solver state
Column *root;              // sentinel
vector<Column*> columns;
vector<Node*> nodes;
int updateCount = 0;
chrono::time_point startTime;
int maxUpdates;
int maxDepth;
milliseconds timeBudget;

// -------------------------------------------------
// Cover / Uncover (O(1) per node – the “dance”)
void cover(Column *c) {
    c->R->L = c->L;  c->L->R = c->R;
    for (Node *i = c->head.D; i != &c->head; i = i->D) {
        for (Node *j = i->R; j != i; j = j->R) {
            j->D->U = j->U;  j->U->D = j->D;
            j->C->size--;
            updateCount++;
        }
    }
}

void uncover(Column *c) {
    for (Node *i = c->head.U; i != &c->head; i = i->U) {
        for (Node *j = i->L; j != i; j = j->L) {
            j->C->size++;
            j->D->U = j;  j->U->D = j;
            updateCount++;
        }
    }
    c->R->L = c;  c->L->R = c;
}

// -------------------------------------------------
// MRV column selection
Column* chooseColumn() {
    Column *best = nullptr;
    int minSize = INT_MAX;
    for (Column *c = root->R; c != root; c = c->R) {
        if (!c->primary) continue;
        if (c->size < minSize) {
            minSize = c->size;
            best = c;
            if (minSize <= 1) break;   // early exit – perfect
        }
    }
    return best;
}

// -------------------------------------------------
// Bounded search
enum Result { Solvable, Unsolvable, Unknown };

Result search(int depth, vector<int>& solution) {
    // Hard bounds
    if (chrono::now() - startTime > timeBudget) return Unknown;
    if (updateCount > maxUpdates) return Unknown;
    if (depth > maxDepth) return Unknown;

    // Success
    if (root->R == root) return Solvable;   // no primary columns left

    Column *c = chooseColumn();
    if (c == nullptr || c->size == 0) return Unsolvable;

    cover(c);
    for (Node *r = c->head.D; r != &c->head; r = r->D) {
        solution.push_back(r->rowId);

        // Cover all other columns in this row
        for (Node *j = r->R; j != r; j = j->R) cover(j->C);

        Result res = search(depth + 1, solution);
        if (res != Unknown) {
            // Clean up and propagate the decisive answer
            for (Node *j = r->L; j != r; j = j->L) uncover(j->C);
            uncover(c);
            return res;
        }

        // Backtrack
        for (Node *j = r->L; j != r; j = j->L) uncover(j->C);
        solution.pop_back();
    }
    uncover(c);
    return Unknown;   // exhausted this branch within budget
}

// Public entry point

    updateCount = 0;
    timeBudget = budget;
    maxUpdates = maxNodes;
    maxDepth = maxD;

    vector<int> solution;
    return search(0, solution);
}

textCopyCopiedusing ColumnSetHash = uint64_t;   // Zobrist or simple sorted-ID hash
